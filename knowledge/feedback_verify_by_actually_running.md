# 단위 테스트가 다 통과해도, 실제로 돌려보기 전엔 '된다'고 말하지 마라

세션49에서 루시에게 컴퓨터 조작(마우스·키보드) 기능을 붙였다. 좌표 환산·검증 게이트·트리거·
승인 게이트까지 **단위 테스트를 전부 통과**했고, 모델이 실제 화면을 보고 올바른 동작을 고르는
드라이런도 성공했다. 그 상태에서 "검증 끝"이라고 보고했다.

그런데 사용자가 "해줘"라고 해서 **진짜로 메모장을 열고 타이핑해 보자, 버그가 3건 나왔다.**
전부 단위 테스트로는 원리상 잡을 수 없는 것들이었다:

1. `open`이 창을 **못 띄우고도 "OK"를 반환** → 다음 타이핑이 직전에 떠 있던 **엉뚱한 창**에
   붙여넣기 됐다. (그 창이 카톡이었으면 남의 대화창에 글이 들어갔다)
2. `Start-Process`가 이 PC에서 아예 실패 (환경 의존 — 다른 PC에선 되니까 코드만 봐선 모른다)
3. 창이 떠도 **맨 앞으로 안 나온다** (윈도우가 배경 프로세스의 포커스 탈취를 막음 — OS 정책)

**Why:** 셋 다 '내 코드의 논리'가 아니라 **바깥 세계(OS·다른 프로그램·타이밍)와 부딪히는 지점**에서
났다. 단위 테스트는 내가 상상한 세계만 검사하므로, 상상하지 못한 것은 영원히 안 잡힌다.
특히 **부작용이 바깥으로 나가는 기능**(마우스·파일·메일·결제)은 실패가 조용하다 —
`open`은 "OK"라고 말했지 예외를 던지지 않았다.

**How to apply:**
- 부작용이 바깥으로 나가는 기능은 **반드시 실물로 한 번 돌리고, 결과를 내 눈으로 되읽어라.**
  (메모장에 넣은 글을 Ctrl+A·Ctrl+C로 **되읽어 대조**한 것이 진짜 검증이었다. 화면 캡처를 눈으로 본 것도)
- "OK를 반환했다"를 성공으로 믿지 마라. **결과물을 직접 확인**하라. (일꾼 모드의 검사관과 같은 원칙 —
  모델도 코드도 안 해놓고 했다고 말한다)
- 검증이 어려워서 못 하겠으면, **못 했다고 정직하게 말하고 사용자에게 넘겨라.** 단, 승인 게이트를
  스텁으로 무력화해서까지 자동 검증하려 들지는 마라(그건 그 기능의 존재 이유를 없애는 짓이다).
